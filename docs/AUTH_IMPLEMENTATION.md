# 인증 구현 문서

## 1. 현재 인증 방식

Day 14에서는 Supabase Auth REST를 사용해 이메일/비밀번호 기반 로그인과 회원가입을 추가했다.

외부 패키지는 설치하지 않았고, 브라우저에서는 공개 가능한 Supabase URL과 공개 키만 사용한다.

## 2. Supabase Auth REST 사용 구조

클라이언트 인증 함수는 `lib/auth/supabaseAuthClient.ts`에 있다.

사용 흐름:

1. 회원가입: 이메일과 비밀번호를 Supabase Auth에 전달한다.
2. 로그인: 이메일과 비밀번호로 세션을 받는다.
3. 세션 저장: 브라우저에 세션을 저장한다.
4. 사용자 확인: 저장된 세션으로 현재 사용자를 확인한다.
5. 로그아웃: 세션을 정리한다.

서버 저장 Route는 로그인 요청에 포함된 인증 정보를 확인하고, 로그인된 사용자라면 사용자 계정 기준으로 저장한다.

## 3. 로그인 상태와 비로그인 체험 상태 차이

비로그인 상태:

- `/demo` 1분 체험을 계속 사용할 수 있다.
- 가게 정보, FAQ, 일정, 생성 기록은 현재 브라우저 기준으로 임시 저장된다.
- 계정 화면에서 로그인과 회원가입을 안내한다.

로그인 상태:

- 가게 정보, FAQ, 일정, 생성 기록이 계정 기준 저장 키로 분리된다.
- `/account`에서 이메일, 무료 체험 플랜, 저장 상태를 확인할 수 있다.
- 로그아웃 후에도 1분 체험은 계속 사용할 수 있다.

## 4. 사용자 ID 기반 저장 분리 구조

Day 14에서는 저장 owner 기준을 다음처럼 나눈다.

- 로그인 사용자: 사용자 ID 기반 계정 저장 키
- 비로그인 사용자: 기존 브라우저별 임시 저장 키

기존 비로그인 체험 기록은 자동으로 계정에 합치지 않는다. 자동 이전은 데이터 충돌과 보안 검토가 필요하므로 이후 단계에서 진행한다.

## 5. 아직 구현하지 않은 것

- 이메일 인증 고도화
- 비밀번호 재설정
- RLS 완전 적용
- 소셜 로그인
- 로그인 전 기록을 계정으로 가져오기
- 결제 상태와 계정 플랜 연동

## 6. 보안 주의

- service role key는 클라이언트에 노출하지 않는다.
- access token과 refresh token은 화면, 로그, 문서에 출력하지 않는다.
- `.env.local`은 Git에 커밋하지 않는다.
- 사용자 화면에는 기술 제공자 이름이나 내부 저장 키를 노출하지 않는다.
- Supabase 테이블 생성 후에는 RLS 정책을 강화해야 한다.
